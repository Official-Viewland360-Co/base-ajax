Remember the argument order

The request method #

request accepts either a URL string or a settings object. With a string, every setting comes from the client. The settings object may carry any configuration option, not just the ones that make sense for a single request.

jsrequest
// Simple
const data = await api.request("https://api.example.com/ping");

// Full
const response = await api.request({
  url: "/reports/monthly",
  method: "POST",
  params: { dryRun: false },     // appended to the query for every method
  data: { from: "2026-01-01" },  // the body (moves to the query for GET/HEAD)
  timeout: 20_000,               // override for this request only
  headers: { "X-Trace": "abc" },
  fullResponse: true,
  retry: { count: 3, delay: 500, methods: ["GET", "POST"] },
  idempotencyKey: true,
});

// A URL object is accepted too
await api.request(new URL("https://api.example.com/health"));
Unknown parameters

Any unrecognised key in the settings (a typo, say) is logged once per client at the warn level and then ignored. Enable logLevel: "warn" or higher to see them.

The callAPI compatibility method #

For projects written against the library's older pattern, callAPI(url, method, data, options, token) is still available. How it differs from request:

  • It always sets responseType: "json" (unless you override it in options).
  • If you omit method it assumes "GET", and data defaults to null.
  • The trailing token argument is used only when options.withAuth === true; otherwise it is ignored.
  • Like the other methods it does not pass through the plugin layer (plugins wrap request and the short methods, not callAPI).
jscallAPI
// GET without a token
const list = await api.callAPI("/users", "GET", { page: 1 });

// POST with an explicit token
const created = await api.callAPI(
  "/users",
  "POST",
  { name: "Ada" },
  { withAuth: true },   // without this option the token is not sent
  "ACCESS_TOKEN",
);

// The modern equivalent:
await api.post("/users", { name: "Ada" });

Merging headers #

  • Header names are normalised to lower case; Content-Type and content-type are the same header.
  • A null value removes an inherited header.
  • If Accept is not set, it defaults to application/json, text/plain, */*.
  • A standard Headers object is accepted too (anything with a forEach method).

Value validation #

  • Invalid values for responseType, methodOverride, logLevel and auth.mode are rejected with a RangeError at construction/configuration time.
  • An invalid request input (empty URL, disallowed method, function/Symbol data, invalid query) becomes an ApiError with the code INVALID_REQUEST.
  • Unknown keys are ignored and logged only once per key per client.
  • A non-numeric or negative timeout falls back to the default (12000); 0, null and Infinity turn it off.

Automatic token refresh (401 â†’ refresh â†’ retry) #

Retry #

retry may be a policy object, a number (the number of retries) or false. The default is count: 0, meaning no retry happens until you turn it on.

How the delay is computed #

  1. The base delay: min(maxDelay, delay Ã— factor^(attempt-1)), where attempt is the number of the attempt that failed (1 for the first one).
  2. With jitter on, the final value is randomised into [wait/2, wait].
  3. If the response carries a Retry-After header (seconds or an HTTP date) and its value is not above maxRetryAfter: wait = max(wait, retryAfter).
  4. If Retry-After is larger than maxRetryAfter, the retry is not performed and the current error is thrown.

When a retry happens #

  • The attempt number has not exceeded count.
  • The error is one of TIMEOUT, NETWORK_ERROR or HTTP_ERROR (ABORTED is never retried).
  • The method is in methods or the request carries an idempotencyKey.
  • For a timeout: onTimeout is on; for a network error: onNetworkError is on.
  • For an HTTP error: the status is in statuses.

The plugin model #

The plugin layer is separate from the core and is published at base-ajax/plugins (or base-ajax/all). Every plugin is a pure function:

jsThe plugin contract
(client, options) => client'   // the original client is never mutated

// client' is a new, frozen object that:
// - has every method and property of the original client
// - wraps the request methods (request + the short methods) with middleware
// - adds its own handle (such as client.cache)

How wrapClient works #

  • A shallow clone of the client is built (rather than a Proxy; this is compatible with non-configurable properties and faster).
  • These methods are wrapped: request, get, head, post, put, patch, delete, options.
  • callAPI is not wrapped; if you need caching, queueing or limiting, use request or the short methods.
  • The result is frozen; neither the original client nor the returned one can be mutated.
  • The middleware signature is (originalFn, methodKey) => (...args) => Promise; methodKey is "REQUEST" for request and the HTTP method name otherwise.
Helper What it does

Plugin order #

compose(client, p1, p2, p3) applies the plugins left to right, so p1 is the outermost layer and the first to see a request. The recommended order, and why:

trace innermost The header should go on the request that is actually sent

Writing a custom plugin #

jsA metrics plugin + a request header
import { wrapClient, optionIndex, withOption } from "base-ajax/plugins";

export function instrument(client, options = {}) {
  const stats = { count: 0, totalMs: 0, errors: 0 };

  const middleware = (originalFn, method) => (...args) => {
    // 1) You may change the arguments (the index of the options object)
    if (method !== "REQUEST") {
      const index = optionIndex(method);
      const current = args[index] || {};
      const headers = { ...(current.headers || {}), "X-Client": "web" };
      args = withOption(args, index, { ...current, headers });
    }

    // 2) Before and after the real call
    const startedAt = performance.now();
    stats.count += 1;
    return originalFn(...args).then(
      (result) => {
        stats.totalMs += performance.now() - startedAt;
        options.onSuccess?.(method);
        return result;
      },
      (error) => {
        stats.errors += 1;
        options.onError?.(error, method);
        throw error;
      },
    );
  };

  // 3) Expose the handle through an accessor so it stays live
  return wrapClient(client, middleware, {
    get stats() {
      return { ...stats, avgMs: stats.count ? stats.totalMs / stats.count : 0 };
    },
  });
}

// Usage

Three important notes about plugins
  • wrapped.create(...) and wrapped.configure(...) come from the base client: create returns a client without the plugin layer, and configure changes the base client's settings.
  • Plugins only see calls that pass through the returned object; if you keep a reference to the original client elsewhere, those calls bypass the plugin layer.
  • The cache/dedupe key is built from the options (including priority); if cache sits outside queue, two requests with different priorities get separate cache entries. For consistency, consume the priority in the outermost layer (queue).

The default key only sees method, url, params and data. If you fire two concurrent requests at the same URL with a different token or header (impersonation, say), they will be merged incorrectly. In that case use keyFn and include the distinguishing fields:

      JSON.stringify(cfg.data ?? null),

Combining with cache

cache on its own does not merge concurrent misses; if two requests arrive before the cache is populated, both go to the network. dedupe solves that: compose(api, dedupe, cache).

Precise details
  • In the closed state any successful response zeroes the failure counter, so "5 consecutive failures" really means consecutive.

  • The state is shared by every request of that client; create a separate client/breaker per service.
  • CircuitOpenError is not an ApiError; handle it separately.
  • While open, an outer breaker blocks cached data too (see the ordering discussion in the previous section).

Behaviour changes that may affect a migration
  • Errors are now always ApiError (they used to be raw Errors sometimes).
  • timeout applies per attempt, not to the whole request.

FAQ and troubleshooting #

Why is no Authorization header sent?

Three common reasons: (1) the default auth.mode is "cookie", which builds no token header; (2) the destination is not trusted, so the token is withheld; (3) no token was stored. With withAuth: true and no token, a warn is logged.

Why is my request to another destination rejected with UNTRUSTED_ORIGIN?

Only the page origin, the baseURL origin and the allowedOrigins entries are trusted. If you really want to send a token to another service, add it to allowedOrigins. For a request without a token, withAuth: false is enough.

Why has my POST become a PUT?

methodOverride defaults to "header" and rewrites PUT/PATCH/DELETE into POST for trusted origins. To switch it off pass methodOverride: false, or change the method list with methodOverrideMethods.

Why do my GET parameters show up in the body?

For GET and HEAD the second argument (and data) becomes the query string and no body is sent. For every other method data is the body, and params is always appended to the query.

Why is no retry happening?

retry.count defaults to zero. Even once configured, a retry only happens for TIMEOUT, NETWORK_ERROR and the listed statuses, and the method must be in retry.methods or the request must carry an idempotencyKey. ABORTED errors are never retried.

Why does the timeout take longer than the configured value?

timeout applies to each attempt. With retry.count: 2 it can take up to three full windows (plus the backoff delays).

Plugins have no effect on callAPI; why?

wrapClient only wraps request and the seven short methods. callAPI is kept for backwards compatibility and bypasses the plugin layer. To get caching, queueing or limiting, use request or the short methods.

Why does cache return stale data?

Check staleWhileRevalidate: with it on, expired data is returned immediately and refreshed in the background. Also note that the cache key excludes headers/token; if the response differs by those, define a custom keyFn.

Blob/ArrayBuffer responses are empty or error out

The jquery transport does not support those two types; use transport: "fetch" or "xhr". Also make sure responseType is set on that individual request.

Where should I handle errors: an interceptor or try/catch?

The recommended split: the error interceptor for global concerns (logging, monitoring, signing out on a 401, normalising messages) and try/catch for each screen's local logic. For â€œa 404 is a valid resultâ€ use validateStatus or recovery inside an interceptor.

Can I use CSRF or cookies in Node.js?

CSRF is designed for the browser and needs a document. In Node, put cookies in headers by hand, set auth: { mode: "none" } and pass an explicit token. Provide origin and allowedOrigins explicitly too.

How do I disable all requests in tests?

Use transport: mock([]) (every route 404s) or a custom transport that returns Promise.reject(new TypeError("network disabled")). With logLevel: "silent" the output stays clean.

Troubleshooting checklist #

  1. Set logLevel: "debug" and read the JSON lines (request:start, request:error).
  2. Use fullResponse: true to see the real status and response headers.
  3. Print client.getConfig() to see the effective settings.
  4. Check whether methodOverride changed the method.
  5. For cache/dedupe issues, build the effective key with client.cache.key(cfg) and compare.
  6. In tests, check the order of the mock handlers (the first match wins).
